# A corpus of prospective admission decisions from a replicated nf-core workflow

Data descriptor, working draft.

## Abstract

Governance claims about automated data pipelines are usually evaluated against
models of the execution engine rather than the engine. This corpus records what
happens when a prospective admission gate — one that decides whether an
operation may proceed *before* it runs, and stops it when the answer is no — is
placed in front of a real workflow engine executing a real bioinformatics
pipeline.

Thirty interleaved replicates of three arms of `nf-core/demo` v1.0.1 under
Nextflow 24.10.5 and rootless podman produced 90 execution traces and 285
admission decision records: an ungated baseline, a gated arm in which every
task is admitted, and a refusal arm in which a declared condition is violated
and the trimming step is stopped before its container starts. Each decision
record carries the verdict, the descriptor version that produced it, the refusal
class where applicable, and every condition that was evaluated with its
expected value, its observed value, and whether it passed — including the
conditions that passed on a refused request.

The corpus supports two kinds of claim that are usually asserted rather than
measured: what an inline governance decision costs in a real engine, and
whether a refusal actually prevents execution. On the first, the decision itself
has a median cost of 11 µs and the process that delivers it 30 ms, a separation
of nearly four orders of magnitude that only replication made visible. On the
second, the trimming step completed zero times in thirty refusal replicates.

## Background & Summary

Dataset descriptors have converged on description. Croissant, RO-Crate, DCAT and
schema.org all say what data is and where it came from; Workflow Run RO-Crate
says what a workflow did. None of them refuses, and a governance mechanism that
cannot refuse has nothing to measure.

Where refusal is claimed — in agent control planes that evaluate an action
against policy inline, before execution — the cost is not published. Our own
prior work has the same gap in the other direction: an EMBC 2026 paper reports a
3.2% latency overhead for descriptor-governed pipelines, but its Nextflow
baseline is a Python program imitating Nextflow and the overhead comes from cost
constants rather than a clock.

This corpus closes that gap for one concrete configuration. Nothing in it is
modelled. Nextflow schedules, containers start, FASTQ files are read, and the
timings come from Nextflow's own trace file.

The one substantive finding beyond the raw records is a separation the original
single-run artifact could not draw. At n=1 the end-to-end difference between the
gated and ungated arms was indistinguishable from noise, and the conclusion
recorded was that the gate's cost sits below the trace's resolution. At n=30 the
per-task difference resolves — +25.7 ms, 95% CI [+3.3, +48.2] — and it is not
the policy evaluation, which is 11 µs. It is the deployment: one Python
interpreter per task, measured separately at 30.2 ms. The claim survives for the
policy engine and fails for the mechanism that delivers it.

## Methods

**Pipeline.** `nf-core/demo` v1.0.1 — FASTQC, SEQTK_TRIM, MULTIQC — over three
paired-end Illumina amplicon samples from `nf-core/test-datasets`. Nextflow
pinned to 24.10.5; 26.04 writes `.command.run` without an execute bit and fails
`nf-core/demo` 1.0.1's strict config parser. Containers via rootless podman with
`podman.mountFlags = 'z'`, without which SELinux relabelling causes every task to
die at exit 126. `executor.queueSize = 1`, so scheduling is serial and a
wall-clock difference is attributable.

**Descriptors.** Three JSON descriptors declare each dataset's lifecycle state
and its permissible actions, each action naming the states that admit it and
conditions over the request context drawn from a closed set of five operators.
The conditions have the shape of a regulated descriptor applied to data that
carries no restriction, so that the corpus can be regenerated by anyone.

**The gate.** Wired in through `process.beforeScript`, which Nextflow executes
in the task's own working directory immediately before the task script; a
non-zero exit fails the task. This is what makes the gate prospective: a refusal
means the tool never runs, as distinct from a provenance record faithfully
reporting that the wrong thing happened. Three refusal classes are kept
separate — undeclared action, state precondition, condition violated — because
they mean different things to a reader of the log.

**Arms.** *baseline*, ungated, identical configuration otherwise. *gated*, every
condition satisfied (`minReadLength = 30` against a policy requiring ≥ 20).
*refuse*, `minReadLength = 10`, which violates the trimming policy.

**Replication.** Thirty replicates, arms **interleaved rather than blocked**, so
that drift in machine state over the run lands on all three arms equally rather
than on whichever arm ran last. Analysis pairs by replicate index, removing the
drift both arms of a replicate share. Work directories are deleted after each
run; only the trace and the decision log are retained.

## Data Records

153 files, 220,867 bytes, 285 decision records. Every file is listed in
`dataset/MANIFEST.json` with a SHA-256 and a record count.

| group | files | contents |
|---|---:|---|
| `runs/replicates/baseline_NN_trace.txt` | 30 | Nextflow trace, 7 tasks each |
| `runs/replicates/gated_NN_trace.txt` | 30 | Nextflow trace, 7 tasks each |
| `runs/replicates/refuse_NN_trace.txt` | 30 | Nextflow trace, 2–4 tasks (the run stops) |
| `results/replicates/decisions_gated_NN.jsonl` | 30 | 210 records, all PERMIT |
| `results/replicates/decisions_refuse_NN.jsonl` | 30 | 75 records: 38 PERMIT, 37 REFUSE |
| `descriptors/*.json` | 3 | the policies that produced every decision |

**Trace files** are Nextflow's own tab-separated format: task id, process name,
status, exit code, `duration` (submit to complete) and `realtime` (the script's
own execution), among others.

**Decision records** are one JSON object per line, carrying `verdict`,
`datasetId`, `descriptorVersion`, `action`, `observedState`, `reasonClass`,
`reasons`, `conditionsChecked` — each with name, operator, expected, observed
and passed — plus `evalMicros` and `wallMicros`. Descriptor version is present
on every record because a decision is only reproducible against the policy that
produced it, and policies change.

`conditionsChecked` records the conditions that **passed** on a refused request
as well as the one that failed. A refusal record listing only the failure cannot
demonstrate that the other rules were evaluated, and demonstrating that is most
of what makes the record evidence.

**Aggregates.** `results/replication.json` holds the paired intervals;
`results/subprocess_cost.json` the process-level timings;
`dataset/gate-decisions.croissant.json` describes the corpus as a policy-bearing
Croissant document, so the corpus is discoverable through the same mechanism it
is about. That document **loads under MLCommons' `mlcroissant` 1.1.0 with zero
errors**, which matters here rather than being a detail: a data descriptor's
machine-readable metadata is only useful if a standard consumer can read it, and
"valid Croissant" is a claim that has to be run rather than asserted.

## Technical Validation

**The microsecond figures replicate.** Median policy evaluation over 210
decisions is 11 µs, matching the 11 µs from the original 7-decision run
exactly. Median gate process time is 119 µs against the published 122 µs.

**The end-to-end effect is real and attributed.** Paired per-task `duration`
delta +25.7 ms, 95% CI [+3.3, +48.2]. Independently, `python3 -m gate` measured
as a process is 30.2 ms median (bare `python3 -c pass` is 9.6 ms), which lies
inside that interval. The overhead is therefore accounted for by the per-task
interpreter rather than left to inference.

**The two trace fields agree on magnitude and disagree on visibility.** Mean
per-task deltas are +25.7 ms (`duration`) and +28.1 ms (`realtime`), but only
`duration` resolves it: Nextflow writes `realtime` at one-second granularity and
`duration` at one-tenth. The earlier "below the measurement floor" statement was
a statement about the floor.

**The refusal is total.** `SEQTK_TRIM` completed zero times in thirty refusal
replicates. This is checked in `bench/aggregate.py` rather than assumed, because
a single counterexample would falsify the artifact rather than widen an
interval.

**Known limits of the corpus.** Per-task deltas are quantized to 0.1 s: 102 of
210 paired tasks show exactly zero and the signal is the asymmetry between 71
tasks at +0.1 s and 19 at −0.1 s, so the interval's direction and order of
magnitude are sound and its endpoints are not precise. The subprocess figure is
this interpreter on this host, not a portable constant. The pipeline is small —
three processes, three samples, roughly 20 s of task time — and demonstrates the
mechanism on real execution rather than at production scale. The RO-Crate output
conforms to the Workflow Run Crate profile's shape but has not been checked with
a profile validator, and nothing here speaks DRS, TES or WES.

## Usage Notes

The corpus answers questions about the *cost and completeness of inline
governance decisions*, not about amplicon sequencing. The reads are public
nf-core test data and the biology is incidental.

Two reuses are direct. Anyone claiming an inline policy check is "negligible"
can be asked for a comparable number; this corpus provides one, together with
the separation between the decision and its delivery that a single aggregate
figure hides. And the decision records are a worked example of what an auditable
refusal contains — including the passing conditions, which is the part usually
omitted.

The full corpus is required for the published intervals. The Croissant
description carries a condition to that effect: an `analyze` action requires
`replicates ≥ 30`, so a consumer reusing a subset is refused rather than quietly
computing a different interval and attributing it here.

## Code Availability

Generation and analysis code is in the same repository as the corpus:
`bench/replicate.sh` (runs), `bench/aggregate.py` (paired intervals),
`bench/measure.py` (single-run comparison), `bench/subprocess_cost.py` (process
timings), `bench/package_corpus.py` (manifest and Croissant description),
`gate/` (the gate itself), `wrapper/wrroc.py` (RO-Crate emission). Everything is
Python standard library; the Nextflow launcher and a Temurin JDK 21 are vendored
under `toolchain/` so nothing is installed system-wide.
